GOROUTINES WAIT (iDLE WHILE DB OR API CALLS), SERVICE (ACTUAL CPU WORK)

wait / service is the ratio of time a goroutine spends blocked to time it spends on CPU.
Breaking it down:

service = T_s = your p95 job time = 3.3975s — the total time a goroutine is "alive" processing one job
wait = the portion of that 3.3975s where the goroutine is blocked — sitting idle waiting on a DB query, Redis call, HTTP response from Monnify, etc.

So if your job looks like this internally:
|-- DB query (0.8s) --|-- Monnify API call (2.1s) --|-- DB write (0.5s) --|-- CPU work (0.5775s) --|
        blocked                  blocked                    blocked               actually on CPU
Then:
wait    = 0.8 + 2.1 + 0.5  = 3.4s   (blocked on IO)
service = 0.5775s                    (actual CPU time)
wait/service = 3.4 / 0.5775 ≈ 5.88

recommendedConcurrency = cores * (1 + 5.88) = 4 * 6.88 ≈ 27
The intuition is: while one goroutine is blocked, the CPU is free — so you need enough goroutines queued up to keep all cores busy during those idle periods.

Why you're using cores * 3 instead
You don't have measured wait and service breakdowns yet, so cores * 3 implicitly assumes roughly a 2:1 wait-to-CPU ratio, which is a reasonable conservative guess for a payment/transfer service that hits a DB and an external API per job.
If you ever instrument your jobs with tracing (OpenTelemetry, etc.), you can replace the * 3 with the real formula:
gorecommendedConcurrency = int(float64(cfg.Machine.CPUCores) * (1 + waitTime/cpuTime))
and make it exact.
